# 证据格式

[English](../evidence-format.md) | 简体中文 | [Русский](../ru-RU/evidence-format.md)

每次手动导出都包含 `manifest.json`、`coverage-draft.json`、`annotation-draft.json`、`quality-receipt.json` 和 `README.txt`。清单记录采集器构建/源码修订、清单各节、操作标记、feature 和特殊按键观测、引导覆盖情况及被拒记录数。其余 JSON 文件提供完整的 OpenBlade 覆盖检查表、范围明确的操作时间窗口和详细的采集质量回执，不包含自动上传或命令重放指令。请参阅[证据 ZIP 的内容](capture-contents.md)。

<a id="inventory"></a>
## 清单

从 Windows 注册表读取的身份信息包括制造商、产品、SKU、BIOS 版本和 BIOS 日期。HID 清单包括 Razer VID/PID、usage、版本和报告结构。相关 Synapse 进程/模块的来源信息包括文件名、版本和哈希。每个设备接口拥有会话内不透明标签。原始实例路径、进程 ID、命令行、用户名和序列号清单字段不会导出。

本地接口路径和 USB 设备层级关系仅保存在内存中，用于附加观测时确认属于同一台实体笔记本。即使设备通过集线器连接，也会保留设备树中最近且匹配的物理 USB 父设备。键盘类 Raw Input 名称通过精确的 SetupAPI 设备实例身份与所选 HID 候选项关联；无法匹配或存在歧义的名称被排除。这些路径和身份信息不会写入导出包的数据对象。枚举不会借用已知机型的命令，描述符匹配也不授予写入许可。

<a id="observations"></a>
## 观测

每次操作都会记录按序生成的 ID、所选接口的准确标签、API、调用进入和返回时间、状态/错误元数据，以及载荷处理结果。输入调用记录与返回缓冲区记录相互独立。实际输出缓冲区容量独立于请求长度记录。尚未完成的原生 I/O 没有已完成响应。`HidD_GetFeature` 不返回实际字节数；`returnedLengthUnknown` 在其成功返回的缓冲区上保留此限制，而 `returnedBytes` 保持 null。此限制与采集丢失无关；完整缓冲区仍可按已审核的隐私规则检查。如果完整观测到一次 API 调用失败，就保留其失败状态和原生错误，并与丢失或不完整的观测分别计数。GET_FEATURE 既可返回设置确认，也可返回查询响应。注释角色和 getter 覆盖依据报告的命令身份，而非传输 API 名称。

仅经过审核的数值型散热、风扇、电池、性能、键盘行为、适配器功率，以及有边界的数值或 RGB 灯效封装，在通过命令专用边界、校验和、保留字节和填充检查后，才可导出其字节。灯效语法覆盖精确的 91 字节行、锁存、亮度、徽标和效果报告，包括 52 字节和 55 字节 RGB 行载荷及经过审核的有效长度效果，以及审核过的 375 字节矩阵帧结构。识别一个值或帧是隐私判断，不证明机型的完整范围、布局或支持。已完成的 HID_GET_FEATURE IOCTL 响应可能包含不带报告 ID 的 90 字节包。它们需要匹配的 91 字节 feature 描述符、至少 91 的输出容量、无缺口的成功完成，以及同样完整的隐私语法检查。导出保留原始 90 字节，报告 ID 为 null。这只是按隐私规则筛选导出数据，并不决定是否支持该命令。未知命令正文仍以元数据保留，附有受限的头部提示和长度，不会仅因陌生就被丢弃。任意 feature 缓冲区可能含标识符，因此仅匹配到 Razer 句柄不足以允许导出载荷。

用户选择或输入的初始、更改和恢复值标记为 `userReported`。“Setting unavailable”（设置不可用）表示用户在 Synapse 中找不到该设置，不表示硬件缺少该能力。完成一张记录卡片只表示用户走完了引导步骤，不代表固件验证完成。

可选的前台特殊按键探测持续五秒，仅保留提示按键策略明确允许的有限输入。预期按键和模式由用户报告。提示产生的事件归入通用输入证据叶项，除非观测到的 Windows 按键或已审核信号能独立识别该信号。普通键入和宏被省略；Fn+P 提示期间的 P 事件不证明 Fn 被按住，也不证明该键控制性能。探测结果与按键行为声明分开；未捕获到输入信号时，不会覆盖先前报告，也不会将已声明的按键标为不可用。

原生队列、单个报告正文、清单标记、可选按键检查和文本仍有界。隐私过滤后的控制观测使用磁盘存储，不再设观测数量、载荷总量或 JSON 条目大小上限；导出时将已完整写入的冻结数据流式保存到一个 ZIP。会话可包含可选的 `storageFailure`，仅记录固定类别和摘要，不含路径或异常消息。被省略的载荷、被拒记录、队列丢失及未完成恢复仍明确可见。原生丢弃计数在每次记录开始时重置，但会话损失和已有证据持续累积。无论是轮询还是停止操作先发现原生失败，都只将其计为一个缺口。若设置更改期间轮询失败，采集器会请求在限定时间内停止自己的观测器，并保留精确初始设置的恢复提醒。即使清理成功，也会保留记录不完整的警告。即使没有操作窗口包含观测，观测器丢失标记也会出现在质量回执中。调用 ID 包含记录前缀，使连续记录中的请求/响应配对保持独立。
ZIP 使用私有临时文件写入，最后原子重命名；关闭 GUI 会等待进行中的导出完成。导出先冻结会话，再将草稿准备和序列化移到 UI 线程之外。所有草稿共享同一组操作窗口。
同时触发停止和关闭时，两者会等待同一次清理完成。正常停止时，或因可恢复的格式错误而拒绝某条记录时，读取器会继续运行，直到原生层完成最后一次队列排空。致命读取器故障会停止该读取器；清理执行最终排空并报告损失。队列丢弃计数独立于记录解析检查，并再次从停止结果检查。
首次等待未能确认停止时，会保留读取器并再等待一次，等待时长仍有限制，以便在最后一次排空前接收迟到的原生完成结果。第二次结果仍未确认时，仍视为部分记录失败。连续格式错误记录保留每条被拒记录的计数，但每次记录只产生一个丢失标记。

准确限制和隐私分类器见 `src/SynapseObserver.Core` 中的 `EvidenceLimits` 和 `FeaturePayloadPrivacy`。维护者应在推导机型专用命令前检查观测层和缺口。

数值范围不是本采集器的生产准入规则。在经过精确审核的散热、Custom CPU/GPU、固定风扇和充电上限命令族内，不熟悉的数值会保留，并标记 `numericMeaningUninterpreted: true`。报告族、控制标签、通道、长度、校验和、填充、来源和状态检查仍然适用。查询输入参数必须符合已审核的全零结构。这样可以保留新机型的数值供研究，但不代表已理解其含义或已支持这些值。

<a id="additive-collection-provenance-in-028"></a>
## 0.2.8 中新增的采集来源信息

会话 v2 记录可以在计算机身份行中包含 `source`，以区分每个注册表视图内的 `BiosRegistry` 和 `SystemInformationRegistry`。质量回执会报告来源缺失或彼此不一致的情况，不会在发生分歧时猜测一个规范产品名称。

操作标记可以包含 `powerSourceAtMarker`，即 Windows 在该标记时采样到的电源来源。仅当所有设置标记均带有同一已知来源时，注释窗口才会公开 `powerSourceAtAction`。样本缺失、未知或发生变化时，特定电源下的性能覆盖仍保持未完成。Windows 显示使用外部电源并不能确定是圆口还是 USB-C 类别，也不能确定适配器功率。清单中的电源信息是初次采集时的另一项独立证据。

容量为 91 字节的已完成 90 字节 feature 响应可以带有 `responseStructureDiagnostics`。固定原因代码会用现有字节同时检查裸数据包和带报告 ID 前缀这两种解释。带前缀的候选项会明确标记缺少末尾填充。诊断信息不包含不透明字节或头部值。仅当偏移后的逻辑字节通过所有可用的不变量检查且首字节被排除时，才会生成范围更窄的 `semanticResponse`。完整的裸数据包解释也不得同时匹配。经过审核的摘要涵盖散热设置确认、散热查询、实际风扇 RPM、已存储风扇目标值、Custom 级别、徽标状态/效果和键盘亮度。摘要保留事务和类型化字段，同时排除首字节、正文和无法取得的末尾填充。`completePayloadRetained` 仍为 false，`headerHints` 仍为 null。设置确认与查询响应不同；RPM 与已保存目标值不同。仅当范围、事务、值和顺序唯一标识一条尚未匹配的设置请求时，注释草稿才会将散热设置确认链接到该请求。所有摘要仍是用户模式返回缓冲区，不是独立的固件确认，也不是完整的 HID 封包。请参阅[针对性采集步骤和来源说明](../control-capture-follow-up.md)。

共享的 `07/0F` 和 `07/8F` 数值电源模式字节使用 `reviewedPowerModeControl`，而不是电池设置投影。其通用 `power.modeControlReports` 覆盖不会根据零值或无关位推断完全充电或 Maximum Fans。

应用与 README.txt 会提供相同的采集检查结果，显示保留的正文、未完成的操作、被省略的响应内容以及剩余证据项目。已记录的操作序列描述的是用户标记，不代表固件回读成功。

HID 描述符还包含输入、输出和 feature 报告中数量受限且经过解析的按钮及数值能力：报告 ID、usage 范围、链接集合、位宽、报告计数、逻辑范围和标志。每个接口最多保留 128 种结构，并明确标记部分完成或被截断的状态。在 HID 解析器 API 1 中，按钮报告计数字段为保留字段，因此其值为 null。这些是描述符元数据；不会采集输入报告正文或普通按键输入。

每个活动显示器还可以带有数量受限的 `colorProfiles` 元数据：所选 Windows 范围、关联的配置文件，以及分别标识的 SDR 和 HDR 默认项。不会推断关联项的子类型。配置文件使用会话内不透明标签。从 Windows 色彩目录按限制读取后，只保留已识别预设的文件名及其 SHA-256 哈希。自定义名称、自定义内容哈希、路径及所有配置文件内容都会被省略。API 缺失、文件无法访问和达到上限会保留为明确的部分结果，不会移除显示模式。

干净结束的记录可以复用由同一个保持打开的采集器验证过的同一观测器 DLL。每次记录都会使用新的映射，并重新检查进程和设备。必须确认挂钩、回调完成、工作线程成功退出以及已加载模块的身份。读取器或证据处理错误会单独阻止复用，不受原生调用及清理状态影响。并发启动不能替换正在进行的记录；清理结果不确定会永久阻止在该 Synapse 进程中复用，迟到的完成结果也不会解除阻止。关闭采集器会丢失已验证的复用记录；使用另一个窗口或构建版本采集前，请重新启动 Synapse。观测器及其固定 Windows API 所有者会保持加载，直到厂商进程退出；其他线程可能仍在使用跳转指令时，不会将其释放。

## 0.2.8 中的推导草稿架构

`coverage-draft.json`、`annotation-draft.json` 和 `quality-receipt.json` 分别使用 `synapse-observer.coverage-draft.v2`、`synapse-observer.annotation-draft.v2` 和 `synapse-observer.quality-receipt.v2`。使用方必须检查每个文件的 `schemaVersion`。外层 `synapse-observer.bundle.v2` 清单以及原始会话/原生协议版本保持不变；这些版本不能决定嵌套草稿的语义。

`7c0c8d7` 之前的开发构建在报告采集器版本 0.2.8 的同时，使用的是 v1 草稿架构。请检查每个文件自身的架构，不要根据采集器版本推断。

注释窗口的 `completeUserReportedSequence` 要求初始、目标、操作和恢复标记按顺序出现，并排除已知相同的初始值和目标值。`unchangedReportedValues` 标识这类排除情况。比较时会去除首尾空白、合并空白分隔符，并使用序号不区分大小写比较；标点及实质性细节保持不变。null 或空白值不会被归为未变化：除此以外顺序正确的序列仍可计为完整并形成能力证据，但其实际值以及设备是否发生变化仍未得到证明。GUI 要求值非空，但底层标记格式允许空值。

质量回执中的 `completeActionWindows` 计数和推导的能力提升使用同一条有效性规则。原始引导覆盖情况和标记保持不变，作为来源依据。注释窗口的单个 `gap` 概括其主要问题；窗口观测仍会单独提供。质量回执记录彼此独立的事实：`UnchangedReportedValues` 或 `IncompleteActionMarkers`，以及窗口中没有 feature 调用观测时的 `NoMatchingObservation`。未变化的空序列会同时保留这两项诊断。恢复到未变化值且已完成的操作不会显示为恢复未完成，但它仍不能证明发生了设置更改。
