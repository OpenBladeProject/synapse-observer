# 证据 ZIP 的内容

[English](../capture-contents.md) | 简体中文 | [Русский](../ru-RU/capture-contents.md)

保存时会生成一个本地 ZIP，不会自动上传任何内容。ZIP 内包含大小受限的 JSON 草稿和一份简短说明。

<a id="manifestjson"></a>
## `manifest.json`

清单是去除敏感信息后的会话记录。它包含采集器构建信息、Windows 身份与支持清单、会话内 HID 标签、已签名驱动和 Synapse 模块的来源信息、操作标记、提示式特殊按键证据、feature 调用观测、引导项目覆盖情况及被拒记录数。

控制操作的观测保留 API、方向、时间、完成状态、所选接口的会话内标签、报告结构和隐私处理结果。只有符合已审核数值格式规则的报告正文才能保留。不熟悉、格式错误、失败、敏感或超限的正文都会被隐去。通过仅在本次会话内有效的 HMAC 比较令牌，以及数量受限的字节变化区间，可以判断两个内容不公开的报告是否相同，而不会生成可长期识别设备的标识符。

<a id="coverage-draftjson"></a>
## `coverage-draft.json`

此文件列出 OpenBlade 格式版本 2 设备覆盖模板中的每个最细分项目，并补充旧模板尚未表达的当前产品要求。Windows 无法确定圆口/USB-C 电源类别或实体按键的功能时，还会保留通用外部电源和提示式输入项目。每项状态为 `NotInvestigated` 或 `Captured`，并引用支持它的 Windows 清单、feature 调用或提示式按键观测。
`Captured` 表示有证据可供审核，不表示已记录整个范围，也不表示查询、设置命令、恢复路径、生命周期路径或生产准入已通过。经 GET_FEATURE 读取的设置确认不会形成 getter 覆盖；命令身份将其与查询响应区分开。经过审核的不完整响应可以保留类型化数值摘要，同时继续排除不透明的首字节和报告正文。散热设置确认需要引用唯一的前一条设置请求，且不会形成 getter 覆盖。经过审核的 getter 摘要需要存在唯一的前一条查询，才能形成 getter 覆盖。实际风扇 RPM 与已存储速度目标值使用不同的叶项。两者都不能证明固件已应用设置或已完成恢复。

<a id="annotation-draftjson"></a>
## `annotation-draft.json`

此文件按范围明确的操作时间窗口，归类操作标记和观测结果。其 v2 草稿包含 `unchangedReportedValues`；已知未变化的选择不会形成完整的设置更改序列。请按照[格式规则](evidence-format.md#derived-draft-schemas-in-028)检查每份草稿的 `schemaVersion`。当前状态报告、跳过、定义和探测意图仍单独保留为 `contextMarkers`，不会创建设置更改或恢复窗口。它还保留特殊按键探测摘要和观测。观测层标签为 `UserModeFeatureApi`、`WindowsRawInput` 和 `WindowsInventory`。

此文件帮助维护者定位相关证据。它不是 USB 抓包、已完成的抓包仓库注释，也不是固件接受请求的证明。

<a id="quality-receiptjson"></a>
## `quality-receipt.json`

质量回执统计已采集及尚未调查的细分覆盖项目、清单缺口、完整操作窗口、已审核报告、被隐去的正文、未关联观测、特殊按键观测及被拒记录。它区分 `ObservedApiFailure`、`CompletionNotObserved` 和仅作提示的 `ReturnedLengthNotProvided` 限制。`CapturePayloadLoss` 表示原生层缓冲区无法读取或受大小限制导致的复制损失，即使 API 成功也可能发生；它与为保护隐私而主动隐去数据不同。观测到 API 失败与采集器丢失数据相互独立。
回执明确列出部分完成、跳过、不可用、失败、取消、隐去及未完成的结果，并记录维护者仍需完成的阶段，将查询验证、设置验证和生产准入声明设为 false。

在 v2 中，`UnchangedReportedValues` 和 `IncompleteActionMarkers` 用于诊断报告序列。`NoMatchingObservation` 单独标识没有 feature 调用的窗口，因此未变化的空序列会同时保留这两项事实。

<a id="readmetxt"></a>
## `README.txt`

此文本文件随证据附上，说明上述信任边界。向支持请求附加 ZIP 时，请保留它及 JSON 文件。

<a id="collection-limits"></a>
## 采集限制

- 隐私过滤后的控制观测会在到达时写入本地临时文件，最后以流式方式导出到一个 ZIP。观测数量、保留载荷总量和 JSON 条目大小不再设固定上限。内存使用保持有界，可保留的数据量取决于本地可用磁盘空间。临时文件仅包含清单中的隐私过滤字段，不保存原始报告或比较密钥。存储失败时会停止采集并明确记录缺口；仅导出完整写入的记录。导出失败或取消后仍可重试。采集及其正在进行的导出关闭后会释放临时证据。
- 步骤中断后会保留准确的起始设置提醒。录制停止后确认的恢复会单独作为用户报告导出，之前的录制序列仍保持不完整。不确认也可保存部分证据。应用为清理预留标记容量。队列丢失通知在每次录制的各操作窗口内合并，保留首次丢失时间和整次录制的最新累计计数。清理失败时仍须手动重启 Synapse。
- 一次记录最长十分钟。
- 实时观测中，一台已识别的实体 Blade 笔记本最多可观测八个 feature 集合。
- 每次观测的 feature 报告最多 4,096 字节，每个原生观测器事件最多 16 KiB。
- 会话最多接受 512 个标记和 128 个引导覆盖项目。达到标记上限后保留已有证据、统计被拒标记，并继续允许停止/导出。独立的覆盖草稿仍包含维护中的完整能力集合，不受引导项目上限限制。
- 特殊按键证据最多 256 条观测，每次提示式探测最多 32 条，探测摘要最多 64 条。达到总量上限时会禁用后续可选按键检查，但设置录制仍可继续。无法保留结果的探测不会显示为正常完成。
- 显示文本最多 256 个字符，不透明标识令牌最多 80 个字符。
- 载荷比较最多保留 64 个流，每次比较最多 16 个变化字节范围。随机 HMAC 密钥随会话销毁，永不导出。
- 清单最多接受 256 个 HID 接口、32 个 Synapse 进程及每进程 256 个模块。支持清单最多接受 32 个 HID 描述符、24 个设备驱动、每驱动 8 个文件和 16 个筛选器、64 个可执行模块、8 个显卡、16 个显示器（各 512 个模式）、16 个亮度条目（各 101 级）、16 个温度区域、8 个处理器及 32 个明确的缺口。最多接受 16 个 LampArray，每个阵列最多 4,096 个灯、256 个按键映射，每个键最多 512 个灯索引。每个接口最多保留 128 种 HID 能力结构；每个查询范围的色彩配置文件列表最多保留 32 个关联项及两条默认配置文件记录。仅对已识别的预设文件计算哈希，每个文件最多读取 16 MiB。
- 导出以流式方式将 JSON 条目写入私有临时 ZIP 并刷新到磁盘，仅当所有条目成功后才替换所选 ZIP。

ZIP 不包含 HID 接口路径、PnP 实例路径、序列号字段、用户名、进程 ID、命令行、账户数据、模块路径或任意进程内存。采集后的工作请参阅[支持所需证据](support-evidence-requirements.md)。

数值范围不是本采集器的生产准入规则。在经过精确审核的散热、Custom CPU/GPU、固定风扇和充电上限命令族内，不熟悉的数值会保留，并标记 `numericMeaningUninterpreted: true`。报告族、控制标签、通道、长度、校验和、填充、来源和状态检查仍然适用。查询输入参数必须符合已审核的全零结构。这样可以保留新机型的数值供研究，但不代表已理解其含义或已支持这些值。

键盘模式属于内部证据。贡献者无需识别 Normal 或 Driver 模式。模式 feature 报告仍保留在被动观测中；提示式按键检查使用 Unknown 模式上下文，不根据按键猜测模式。

色彩配置文件证据包括 Windows 关联项以及 SDR/HDR 默认项，不包含配置文件内容，也不能证明校准或色域准确性。采集器尚未枚举陌生原生亮度驱动栈所需的独立控制接口和虚拟接口拓扑。驱动文件签名检查也不会单独验证目录签名，因此 `Unsigned` 结果不能证明 Windows 驱动缺少有效的目录签名。这些采集限制会列入质量回执。

可选按键检查也会监听符合条件、顶层用途未定义的 Generic Desktop 输入集合。Windows 将该用途页的输入发送给前台收集器，收集器先核对设备，再读取报告正文。鼠标数据和无关设备会被忽略，未知报告的内容仍会隐藏。只要已取得顶层用途和输入报告长度，可选描述符细节不完整也不会阻止检查。输入被拒绝、检查中断或无法进行，会与检查正常结束但未收到输入的情况分别记录。
